# Widen the engine's search before judging

**In plain terms:** the engine finds small wins on real libraries mostly because of how it asks for ideas. Today one cheap call writes five ideas without ever seeing the code, the engine trials them in the order the model gave, and it stops at the first win. The research points the same way from four sides. Models give the same few textbook answers unless they are made to look from different, independent angles. Their own judgement of which idea is "novel" is unreliable. And the systems that found big wins (AlphaEvolve, FunSearch) got them by generating many varied candidates, measuring each one for real and feeding the results back, not by writing cleverer prompts. **We propose** replacing the single call with a **five-stage idea pipeline** inside the existing `HypothesisGenerator` seam: (0) read the hot code; (1) keep today's "obvious" ideas as one lane; (2) run six or seven independent "lens" calls, each built on one proven idea framework (remove assumptions, compute the lower bound, name the underlying problem, recombine, resolve the trade-off, plus one deliberately far lane); (3) a fresh-context Opus 5.5 reviewer that removes only ideas that clearly cannot work in this code; (4) a **deterministic portfolio rule**, not an LLM score, that picks 3-5 non-obvious ideas to trial next to the obvious ones. The judges, the anti-cheating rules, the output check, the noise rule, the single fix retry, the cost cap and the parked `novel` class all stay as they are. Generation is cents today and trials dominate cost, so the pipeline costs roughly $0.6-1.1 a run (our estimate). That fits a $5 run, but only if the discovery share is raised for its worst-case pre-check. A staged set of live experiments costing about **$120 of Window 1's ~$182** compares Sonnet 5.5, Opus 5.5 and Fable 5.1 in the roles where they could differ, and tests on the ten real libraries whether the pipeline beats today's generator. Set expectations honestly: the best-measured lever in this repo is still iteration (evolution rounds roughly tripled cumulative gains). The pipeline is a well-founded bet that must earn its place in the same A/B instrument as everything else. Some "never improves" results may come from a rule or harness artefact, not from weak ideas, and a free check should run first.

## Today's generator writes five ideas from numbers, never from code

The current pipeline is easy to describe because it is small. When the candidate pool is empty, the hypotheses node makes one structured-output request to **Sonnet 5.5 at medium effort for at most five ideas**, and at most two such calls per run (`services/python_agents/src/autonomous_ai_agents/common/config.py:193-260`; `orchestrator/nodes.py:888-1026`). The request carries the project name, the objective, the understander's prose summary and up to 40 profiler rows, but **no file contents**. Only the understander reads code (`optimization/generate.py:211-244`; `orchestrator/understand.py:1-30`). Nothing critiques, refines or compares the ideas. Generated ideas keep the model's order, because a generated `expected_gain` is uncalibrated: Opus claimed big gains on the `lettertally` control at every effort (`optimization/ranking.py:63-101`; `STATUS.md:1786-1788`). Each round trials three ideas, and **the router ends exploration at the first `keep`** (`orchestrator/nodes.py:3329-3346`). Lessons are saved after every run but never match a new idea in blind mode, so nothing learned flows back yet (spec D21, `.claude/handoff/step3/spec.md:377-382`).

On the synthetic corpora this saturates: 22/22 hit@5, 44/44 wins, 10/10 on the hard set. So those sets cannot tell a better idea pipeline from a worse one (`STATUS.md:1590-1593`, `2056-2059`). Real libraries are different. In the wired Window 1 runs, the Opus-editor arm delivered 7/10: tabulate 47.2 %, pycparser 27.7 %, idna 15.5 %, then a tail of 9.5, 8.8, 6.1 and 2.6 %. **more_itertools, pyparsing and tomli delivered nothing, with best trials of 1.8-3.8 %**, against per-project noise floors of 2.0-5.9 % (`STATUS.md:1611`, `1616`). The Sonnet-editor arm added sortedcontainers to the never list (`STATUS.md:1615`). Two more findings frame the problem. Trying more ideas helps up to about five and then stops helping (win@1 6-7/20, win@5 12-13/20, win@10 no better), and on tabulate **the rank-1 idea was never the one kept** (`STATUS.md:1603-1604`, `1649-1651`). And the strongest lever measured so far is depth, not breadth: re-baselined evolution rounds took mean cumulative gains from 22.0 % to 34.7 % in one run and from 9.8 % to 30.7 % in another, with every re-test holding, and sqlparse was still improving at round 10 (`STATUS.md:1605-1607`, `1641-1656`).

The diagnosis follows from the code, though it is an inference, not a measurement. A generator that sees only "function X takes 31 % of the time" plus a summary can propose only a textbook idiom for X. It cannot see the data shapes, invariants or algorithmic structure that a non-obvious change depends on. The forbid-list (no dependencies, no processes, output identical, no code) also puts the families with the biggest usual payoffs out of reach: process pools, native code, and numpy where it is not already a dependency. Inside pure Python, the remaining routes to large gains are algorithmic and representational. Those are exactly the ideas a profile-only prompt cannot ground.

One caveat must come before any blame lands on the ideas. In L2a, the `process_spawn` rule refused trials on **more_itertools and tomli in both repetitions** (and mistune once), and STATUS does not explain why. The rule scans the whole new blob of each modified file (`optimization/anticheat.py:738-763`). So a module that already imports a spawn-related library could be refused whatever the edit does. Two of the four "never improves" libraries may therefore be partly a rule artefact. A free offline check should settle this first (experiment E0).

## Research agrees: breadth comes from independent lenses, wins from measurement

**Models converge, and asking for more of the same does not fix it.** In the largest blinded study, LLM research ideas were rated more novel than experts' (5.64 vs 4.84). Yet of 4,000 seed ideas per topic, only about 5 % were non-duplicates, and the authors found that generating more "simply leads to repeating duplicate ideas" ([Si, Yang, Hashimoto, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/ea94957d81b1c1caf87ef5319fa6b467-Paper-Conference.pdf)). The same pattern holds across models. Frontier models give fewer than four distinct answers in ten samples, and larger models in a family are often *less* diverse ([NoveltyBench](https://arxiv.org/html/2504.05228v1)). Different model families converge on the same ideas ([Artificial Hivemind, NeurIPS 2025](https://arxiv.org/abs/2510.22954)). Twenty-two LLMs together vary far less than 100+ humans (population variability on an unusual-uses task 0.459 vs 0.738) ([Wenger and Kenett](https://arxiv.org/pdf/2501.19361)). Temperature is a weak lever ([Peeperkorn et al., ICCC 2024](https://arxiv.org/pdf/2405.00492)), and on Opus 5.5 and Fable 5.1 it is gone entirely: non-default sampling parameters return a 400 ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). **Diversity has to come from the prompt and the pipeline.**

**What measurably widens the pool.** The training-free levers with numbers behind them each change the *conditions* of generation. Verbalized sampling asks for several answers with their probabilities. It raised diversity 1.6-2.1x in creative writing, and larger models gained more ([Zhang et al.](https://arxiv.org/abs/2510.01171)). In a test of 35 prompting strategies, "generate many short distinct ideas, then make them bold and different" gave the most diverse pool ([Meincke, Mollick, Terwiesch](https://papers.ssrn.com/abstract=4708466)). Chain of thought reduces LLM fixation on early outputs, and ordinary varied personas beat famous "creative" ones ([Deng, Brucks, Toubia](https://business.columbia.edu/faculty/research/examining-and-addressing-barriers-diversity-llm-generated-ideas)). Conditioning each round on different retrieved material gave 3.4x more unique novel ideas than the same pipeline without it ([Nova](https://arxiv.org/pdf/2410.14255)). The human literature agrees on the process. People working alone and pooled beat interactive groups, mainly because one shared stream blocks production ([Diehl and Stroebe 1987](https://doi.org/10.1037/0022-3514.53.3.497)). And later ideas in a session are more original than early ones, because the first ideas are the accessible, common ones ([Beaty and Silvia 2012](https://beatylab.la.psu.edu/files/2020/08/2012_Beaty_PACA.pdf)). For the engine this means several independent calls, each with a different lens and its own fresh context, which all start *after* the obvious ideas have been named and set aside.

**Which idea frameworks are worth forcing.** The evidence ranks them unevenly, and the ranking drives the lane design. The strongest cognitive evidence is for **representational change**: impasses break through *constraint relaxation* (dropping an assumption the goal does not require) and *chunk decomposition* (breaking a familiar operation into parts) ([Knoblich et al. 1999](https://www.kognition.uni-koeln.de/literature/Knoblich_etal_1999.pdf)). The strongest evidence on where valuable novelty comes from is **recombination**. Across 17.9 million papers, the highest-impact work pairs a conventional base with one atypical combination ([Uzzi et al., Science 2013](https://www.kellogg.northwestern.edu/faculty/uzzi/htm/papers/Science-2013-Uzzi-468-72.pdf)), and novel combinations raise the *variance* of outcomes more than the mean ([Fleming 2001](https://doi.org/10.1287/mnsc.47.1.117.10671)). That suits an engine whose judges cut off the downside. **TRIZ** has only moderate, small-study evidence ([Polimi thesis](https://www.politesi.polimi.it/handle/10589/132061)), but it is already LLM-automated ([AutoTRIZ](https://arxiv.org/abs/2403.13002v1)). It fits time-versus-memory-versus-exactness trade-offs well, and its "no compromise" demand directly counters the LLM habit of returning the textbook trade-off. **SCAMPER, de Bono and Synectics** show only marginal effects ([SCAMPER studies](https://www.edgehill.ac.uk/?p=198123)), so they are cheap diversity injectors at most. Performance engineering also has its own catalogue of transformations: Bentley's rules, including space-for-time, data-structure augmentation, precomputation, lazy evaluation and loop fusion ([MIT 6.172](https://ocw.tau.edu.ng/courses/electrical-engineering-and-computer-science/6-172-performance-engineering-of-software-systems-fall-2018/lecture-2-bentley-rules-for-optimizing-work)). It works best as the dimensions of a morphological box, not as an answer list. No study tests any of these frameworks as prompts for code performance. Their value here is as **coverage-forcing devices** whose payoff the engine's own trials must measure.

**What made program search find big wins.** Every system that reported breakthroughs shares one loop: a database of scored candidates with diversity control, prompts built from several prior candidates plus their *measured* results, diffs as edits, and a cascade of automatic evaluators from cheap to expensive. AlphaEvolve pairs a fast model for volume with a strong model for "occasional, higher-quality suggestions". Its ablations show that each part matters: removing evolution, the prompt context, meta-prompt evolution or the strong model each made results worse ([AlphaEvolve white paper](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/AlphaEvolve.pdf)). FunSearch found that showing **two** prior programs beats one, with diminishing returns beyond that ([FunSearch manuscript](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/Mathematical-discoveries-from-program-search-with-large-language-models.pdf)). When evaluation is expensive, as an engine trial is, the efficient regime is ShinkaEvolve's: reject near-duplicate candidates *before* evaluating them, and reach results in about 150 evaluations instead of FunSearch's ~10^6 ([ShinkaEvolve README](https://github.com/SakanaAI/ShinkaEvolve)). At a fixed budget of 10 calls, refinement with execution and profiler feedback beat independent sampling in 5 of 6 KernelBench settings ([KernelBench](https://scalingintelligence.stanford.edu/pubs/kernelbench.pdf)). The real-system wins were also more modest than the headlines. AlphaEvolve's 23 % kernel speed-up meant 1 % of end-to-end training time. On real repositories, agents reach only about 0.15-0.23x of expert speed-ups ([SWE-fficiency, ICML 2026](https://proceedings.mlr.press/v306/ma26l.html)). Every famous failure was an evaluator failure, such as Sakana's kernels that skipped the computation ([Techmeme/TechCrunch](https://www.techmeme.com/250221/p22)) or OpenEvolve's 2.8x claim that became 3.2 % *slower* once the harness was fixed ([OpenEvolve MLX example](https://github.com/algorithmicsuperintelligence/openevolve/tree/main/examples/mlx_metal_kernel_opt)). The engine's frozen judges are its strongest asset. The weakness is upstream, in what gets proposed.

**Why the engine must not trust a model's own novelty rating.** After 43 experts actually built ideas, the LLM ideas' scores fell significantly more than human ideas', and the ideation-stage novelty advantage disappeared ([The Ideation-Execution Gap](https://arxiv.org/abs/2506.20803)). LLM novelty judges flip on more than half of identical pairs after a small prompt change ([Old Ideas, Novel Problems](https://arxiv.org/html/2610.02022)). They also show a "novelty mirage" that favours model-written ideas, which human experts reverse ([On the Limits of LLM-as-Judge](https://www.alphaxiv.org/abs/2606.12071)). Intrinsic self-correction without external feedback is unreliable and can make answers worse ([Huang et al., ICLR 2024](https://arxiv.org/pdf/2310.01798)). The engine's rule "ranked by verdicts and lessons, never by an LLM novelty score" (`STATUS.md:1762-1766`) is therefore well founded, and the design below keeps it.

## Claude 5 models reward stated goals, named defaults and effort, not choreography

Anthropic's current guidance for Fable 5.1, Opus 5.5 and Sonnet 5.5 changes how the lanes should be written. **State the goal, the constraints and the reason for each constraint, not a step-by-step plan.** "A prompt such as 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan", and explaining *why* a rule exists lets the model generalise ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Fable 5.1 in particular finds prompts written for earlier models "too prescriptive" ([Prompting Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1); taken from the local skill mirror, not fetched live). **Put long data first and the ask last**, in descriptive XML tags. Use **3-5 varied examples labelled illustrative**, framed as problem, then method, then expected result; examples shape how the model thinks, so they also anchor it. And **do not ask for written-out reasoning**. On these models a request for `<thinking>`-style output can be declined as `reasoning_extraction`, so ask for a short justification instead ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices); [Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). The engine already learned the schema version of this the hard way: a field named `reasoning` drew billed refusals, so it uses `justification_summary` (`STATUS.md:1669-1683`).

The most directly useful finding for divergence comes from the Opus 5.5 guide. A generic instruction to avoid generic output "mostly swaps one default for another". Instead, the model "responds well to instructions that name specific patterns to avoid", and the list should grow as each round reveals the next default ([Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). That maps onto the pipeline exactly: lane prompts name the obvious-lane ideas, the playbook titles and `avoid_titles` as "already on the table". Pressure language ("CRITICAL", "think outside the box!") is treated as cruft, and so is grader vocabulary. Give the model permission to return fewer ideas or none: admitting uncertainty "can drastically reduce false information" ([Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)).

**Effort is the depth lever, and its defaults differ by model.** Opus 5.5 defaults to `medium`; Fable 5.1 and Sonnet 5.5 default to `high`. Thinking cannot be turned off on Opus 5.5 or Fable 5.1, and lowering effort reduces thinking "more reliably than prompt instructions do" ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort); [Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). The same caveat as the earlier report applies: past generator comparisons mixed effort defaults. With structured outputs, Sonnet 5.5 can only reason in its thinking. The guide's fix is the line "Think the problem through before you answer.", which at `high` brings accuracy close to `xhigh`. It also warns that at `low`/`medium` the model occasionally thinks until `max_tokens`, so treat that stop reason as a failure even when the JSON looks valid ([Prompting Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Caching rewards one byte-stable prefix: system prompt, then code and profile, then the lane-specific instruction after the last breakpoint. Caches are model-scoped, and changing top-level effort between requests breaks them; per-message effort (beta) avoids that ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort)).

**Roles the models are suited to, from Anthropic's own descriptions.** Sonnet 5.5 ($2/$10 per MTok) is the fast everyday coding model, though "for the hardest long-horizon work, an Opus model is the better choice" ([Prompting Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)). Opus 5.5 ($4/$20) has "stronger code review, with more bugs caught ... and fewer false alarms" and is "much less likely to state an incorrect figure" ([Prompting Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). That makes it the natural fresh-context reviewer. Fable 5.1 ($10/$50) is the most capable widely released model. Its guide advises starting it "at the top of your difficulty range". It deliberates beyond need on routine work, roughly doubles output at `xhigh` on long deliverables, and needs **30-day data retention**, which matters when a user's code is the input ([Prompting Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1), local mirror). The Fable guide also says "separate fresh-context verifier sub-agents tend to outperform self-critique", which supports a reviewer that did not write the ideas. The engine's own evidence is thin but real. On the saturated corpus, Fable matched Sonnet's hit rate at 7x the cost, and Opus at high twice returned nothing (`STATUS.md:1590-1592`). Neither result says anything about non-obvious ideas, because that corpus had none.

## A five-stage idea pipeline that fits the existing seam

The whole pipeline lives inside one implementation of the existing `HypothesisGenerator` Protocol (`optimization/sources.py:34-67`). It returns `GenerateResult` through the existing `_hypotheses` validation and the node's `_sift`, so the node, the judges, the anti-cheat rules and the budget accounting do not change. Its spend is read from the Budget delta like any other discovery call (`orchestrator/nodes.py:926-936`).

```
S0 read code (no model) ──► S1 obvious lane (Sonnet med) ──► "already on the table" list
                                     │                                   │
                                     ▼                                   ▼
                     S2 six lens lanes (Sonnet med, parallel, fresh contexts, shared cache)
                       + one leap lane (Opus 5.5 high; Fable 5.1 high in E1 arm D)
                                     │
                                     ▼
              S3 fresh-context reviewer (Opus 5.5 high): ground in code, prune only
                                     │
                                     ▼
       S4 deterministic portfolio (code): dedup, Amdahl and noise gate, quotas, order
                                     │
                                     ▼
      existing trials ─► judges ─► verdicts ─► combine (unchanged); portfolio round completes
```

| Stage | Model and effort | What it sees | What it returns |
| --- | --- | --- | --- |
| **S0 Code context** | None (deterministic) | Base-commit source of the top hotspot functions by *cumulative* share, plus their direct callers, read through the understander's fenced, read-deny-respecting path; size-capped (about 15-25k tokens); a call-tree summary, not only self-time rows | One cached document block; per-hotspot **Amdahl ceiling** (a change to a function cannot gain more than its cumulative share) next to the project's measured noise floor |
| **S1 Obvious lane** | Sonnet 5.5, `medium` (today's generator, now with code) | S0 block, objective, understanding, playbook titles, `avoid_titles` | Up to 5 ideas. They are both trial candidates and the "named defaults" list for S2. This keeps today's measured baseline inside the new arm. |
| **S2 Lens lanes** (6) | Sonnet 5.5, `medium` (E1b tests `low`); parallel, same model so the prefix cache is shared | S0 block + S1 list as "already on the table" + one lens goal + 2-3 rotating illustrative examples from a *different* codebase | Up to 6 ideas per lane, each with the exact code lines it depends on, its precondition, an equivalence argument, morphological cells, and a typicality guess used only for logging |
| **S2 Leap lane** (1) | Opus 5.5, `high` (set explicitly; default is `medium`) | Same, framed as "the textbook ideas were tried and won little here" | Up to 3 ideas, same schema |
| **S3 Reviewer** | Opus 5.5, `high`, fresh context, did not write the lane ideas | S0 block + all S1/S2 ideas fenced as untrusted model text | For each idea, one of `feasible`, `unknown` or `infeasible:<enumerated reason>`; for `feasible`/`unknown`, a concrete change plan in words naming functions and steps. It never scores or orders. |
| **S4 Portfolio** | None (code); optional Haiku 5.5 `low` "same mechanism?" check on near-duplicate pairs | Reviewer output, lessons, avoid_titles, playbook | Up to 5 obvious ideas + **3-5 non-obvious ideas**, in a fixed interleaved order |

**The six lenses** are the frameworks the evidence ranks highest, each turned into a goal. *Eliminate* (first principles and TRIZ's Ideal Final Result): state the least work the exact output logically requires, then target each step the code does beyond it. *Assume less* (constraint relaxation and chunk decomposition): list the code's implicit assumptions (recompute every call, hold everything in memory, process in input order, use general-purpose objects), mark each as required or not by the objective, and break one high-level library call into its parts. *Name the problem* (Polya's "generalise" plus near and moderate structure-mapping): restate the hot computation relationally, without domain nouns, name its general problem class and best-known algorithm, and borrow from databases, compilers, operating systems or numerical analysis. *Recombine* (a morphological box over Bentley-style dimensions: work elimination, timing, granularity, representation, algorithm class, memory lifetime): propose cells that differ from the current code in at least two dimensions, with a conventional base plus one atypical element. *Resolve the trade-off* (TRIZ contradictions and the four separation principles: in time, in space, by condition, by scale): name the trade-off a normal fix would accept, then remove it. *Far* (provocation and far analogy, bounded to this one lane): start from a deliberately false statement ("the input never changes") or a non-computing domain, and extract a mechanism. Each idea carries its lane, its cells and its Boden tier (combinational, exploratory or transformational). Wave 2 only records these tags, so a later lessons archive can learn which lens pays off where. No published study answers that for software.

**Prompt structure, the same for every lane.** The system prompt is byte-stable and cached across lanes. It holds a one-line role ("You are a performance engineer proposing speed-up and memory-reduction ideas for an automated optimisation engine"). It explains, with reasons, what happens to an idea: each one is trialled in an isolated copy and measured repeatedly, and it is kept only when the output is identical and the gain clears the project's noise floor. It also says why each rule exists. Test, benchmark and measurement files are frozen so measurements stay independent. New dependencies need separate vetting. Processes and threads are excluded because CPU time and peak memory are measured per process. Then come the change classes in plain words, the existing untrusted-data fence policy, "describe changes in words; never write code", and explicit permission to return fewer ideas or none. The user turn puts the long data first: `<documents>` holding the fenced code with paths and line numbers, the call-tree profile, the understanding and the objective with its floor. Then come `<already_on_the_table>` (the S1 titles, playbook titles and avoid_titles) and the cache breakpoint. After the breakpoint sit the lens goal, the illustrative examples and the ask:

```
<lens>Assume less. Every fast path starts from an assumption the slow code keeps
without needing it. Find assumptions the objective does not require, and build each
idea on dropping one.</lens>
<examples note="illustrative only, from other codebases; do not copy their technique">…2-3 problem → method → result examples, rotated per run…</examples>
Propose up to 6 ideas that are not variants of anything in <already_on_the_table>.
Include at least two that you think a typical performance engineer would be unlikely
to suggest. For each idea, quote the exact lines it depends on and say why the
program's output stays identical. Think the problem through before you answer.
```

The quoted lines enable a **deterministic grounding check**. The engine verifies that each quote is a literal substring of the S0 code it showed, and drops ideas whose quotes are not, in the same spirit as the earlier report's citation check. The schema extends `GENERATE_SCHEMA` with `depends_on_quote`, `precondition`, `equivalence_summary`, `morph_cells` (enum), `lane` (set by the engine, not the model) and `typicality` (logged only). It names no field `reasoning`, `thinking` or `trace`, and it has no length keywords. Two hygiene rules apply. First, the model never labels an idea's origin. Today an LLM-chosen `change_class: novel` is parked as "needs approval" (`orchestrator/nodes.py:938-966`). In this engine "novel" means *unverifiable*, not *original*, and a highly original idea that keeps output identical is `efficiency` and can be delivered automatically. The prompt should explain the classes in those terms, and origin should live in `lane`. Second, a `max_tokens` or `refusal` stop counts as a failed lane: the engine drops that lane and does not retry it, so the cost bound holds.

**The reviewer prompt** (S3) is short on rules and specific about its single job. "You check whether proposed changes can work in this code. You do not judge originality or likely size of gain." For each idea it returns `feasible`, `unknown` or `infeasible` with one enumerated reason: violates a stated constraint; precondition false at the quoted line; cannot keep the output identical; duplicate of idea k; or targets code outside the hot path. It returns `unknown` whenever it is unsure, because the judges are the real test. For ideas that survive, it writes a concrete change plan, which is meant to reduce the editor's rediscovery work. That matters because Opus edits real code successfully only 12 times in 20 even with aimed ideas (`STATUS.md:1606`). The reviewer runs in a fresh context on a different model from the lane generator, as Anthropic's verifier guidance suggests. Its output is model text, so it re-enters `_hypotheses` and `_sift` fenced like any other.

**Selection without a novelty score (S4).** The S4 rule runs in code, step by step. First it drops ideas that fail validation, the grounding check or the reviewer. Next, the Amdahl and noise gate removes any idea whose targeted functions' combined cumulative share is below about 1.5x the project floor. Such an idea cannot clear the noise even if it removes all of their time, which is the likely story of best trials of 1.3-6.7 % against floors of 2-5.9 %. Then it deduplicates by a structural signature (target symbol plus morphological cells plus mechanism family), with the optional Haiku check only on pairs that collide. It defines **non-obvious structurally**: an idea counts only if its signature differs from every S1 idea, every playbook card and every lesson or avoid_title. That is retrieval-based novelty, the stable kind, not an LLM judgement. Finally it picks 3-5 non-obvious ideas by **coverage quotas**: at most one per lane, at most one per morphological cell, at least two different target functions, and at least one transformational-tier idea when one survives. Within a lane it keeps model order, and the lane order rotates each run from a seed. The trial order then interleaves the two pools: round 1 runs S1#1, N#1 and N#2; round 2 runs S1#2, N#3 and N#4; and so on. Two spec changes make this work, and both need the owner's approval. D8 gains a clause: "generated ideas are ordered by a deterministic portfolio rule across lanes, model order within a lane; no model-written score reorders them". The router also gains a bounded `complete_portfolio_round` setting, so the first `keep` no longer ends exploration before the non-obvious ideas get their trials. The cost cap still binds, and COMBINE still stacks whatever wins.

**How the existing constraints apply.** The frozen judges, the protected-file rules, `process_spawn` and the output check are untouched; the pipeline only changes what is proposed and in what order. The noise rule (paired ABBA, confirmation before keep, per-project floor) decides every keep, and the Amdahl gate simply avoids spending trials the noise rule would reject. The single fix retry per run stays at one: concrete change plans should cause fewer fixable crashes, but the retry budget does not grow. Ideas that change output go to `behaviour` and the review branch, and `novel` stays parked. All calls are tool-free, all repository and model text stays fenced, and nothing a lane writes can run code. For **cost**, using list prices and a 20k-token code prefix, S1 is about $0.08, six Sonnet lanes about $0.25-0.30, the Opus leap lane about $0.28 and the Opus reviewer about $0.35. That totals **$0.6-1.1 per run, an estimate to confirm with `count_tokens` in E0.** The binding limit is the worst-case pre-check (`Budget.check`), not the expected spend. With lane `max_tokens` at 8k, the worst case is about $1.6, above D7's $1.25 (25 % of a $5 cap). So the experiment arm needs `DISCOVERY_MAX_SHARE` at 0.35-0.40, which is an owner-visible setting, or a smaller reviewer `max_tokens`. Trialling 8-10 ideas instead of today's 3-8 adds roughly $0.3-0.5 of editor spend, so a full run should cost about $1.6-2.0. The build is four units of at most about 400 lines each: the S0 code packer and Amdahl table; the lane prompts, schema and grounding validator; the reviewer and the S4 portfolio; and the router setting, V4 arm wiring and a recorded fixture for offline replay (D20's `ScriptedTransport` eval). That is beyond the approved V1-V6 list, so **it needs the owner's approval as a Wave 2 addition**, ideally as arm C of V4's A/B instrument, which already exists to compare discovery arms.

## Conclusion

The research changes the question from "how do we prompt for brilliance?" to "how do we stop the engine from asking the same question five times?". Every credible source of large wins, from FunSearch to AlphaEvolve to this repo's own evolution runs, couples broad, deliberately varied proposals to real measurement and then iterates. None relies on a model recognising its own best idea, and execution data shows that the ideas models rate most novel are the ones that fade most when built. So the most important design choices here are structural, not rhetorical: let the generator read the code, name the obvious answers so the lanes can move past them, keep the lanes independent, prune only on checkable grounds, choose the portfolio by coverage rule, and stop letting the first win end exploration.

Two implications reach beyond Wave 2. First, the engine's "novel" label is overloaded. It means "cannot be verified automatically", which is the opposite of what an original but provably equivalent speed-up is. Separating origin from verifiability is what lets the engine pursue groundbreaking ideas without giving up autonomy proportional to verifiability. Second, the four libraries that never improve may be telling us about the engine's own boundaries, its spawn rule, its pure-Python scope and its noise floors, as much as about idea quality. If E0 and E1 show there is no Amdahl-feasible, rule-compatible headroom there, the next big gains come from capability acquisition (Step 3b) and from iteration, not from better ideation. Knowing that early is worth more than any prompt.
